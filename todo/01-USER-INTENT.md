# 用户意图：产品与 Apple 应用基础框架

> AI 开始工作时先读本文，再读 `00-START-HERE.md`，最后只读取当前任务必要的设计与代码。
> 本文记录用户希望得到的结果与合作方式，不宣称现有代码已经实现这些要求。用户最新明确指令优先。

## 1. 我究竟想做什么

我想把当前 App 做成真正好用、完整、可靠的 Apple 原生产品，并在实际开发中形成一套能够支持未来五年多种产品的应用基础框架。

这两件事需要共同推进：产品不能沦为框架演示；框架不能成为只适用于当前业务的一堆封装。我需要稳定的应用组织方式、清晰的扩展边界和可复用的交互语义，让以后做新产品时，不必重新解决窗口、场景、导航、命令、状态和基础界面的组织问题。

当前仓库以 MSRU 音乐应用为实际落地点。音乐业务用于验证框架，但不应变成框架的前提。未来产品可能具有不同对象、流程、界面和服务端需求，不要求都长得像音乐应用。

“五年指导”意味着原则和边界能持续使用，不意味着现在预测、实现未来五年的全部功能，也不意味着某个 API 或视觉细节五年不变。

## 2. 我希望最终看到什么

- 一个真正能运行、能够持续维护的产品；主要流程有完整的开始、进行、完成、失败与恢复行为。
- 一套体量克制、职责清楚的基础框架；应用可以组合它，而不必迁就它。
- 一个清晰的仓库：现行实现容易找到，旧版本退出主路径，目录反映职责。
- 一套相互连接的长期文档：意图、架构、交互、技术边界、工作队列和验证标准各有位置。
- AI 接手时能迅速知道用户要什么、当前任务依据什么、需要改哪里、完成后如何验证。

不要把“写了很多抽象”“画了很多图”“测试数量增加”当作完成。完成应体现在产品行为明确、实现一致、使用自然、维护成本可控。

## 3. 产品与视觉偏好

### Apple 原生是明确方向

我希望获得 Apple 原生应用的体验，重视系统当前的 Liquid Glass 视觉方向、原生控件、窗口行为、导航、菜单、键盘操作和平台习惯。

“原生”不只是给自绘面板加透明、模糊和圆角。应优先使用系统提供的组件与材质，让界面随平台自然演进。内容应清晰，导航与操作层级应明确；不要为了玻璃效果把所有内容都做成半透明卡片。

macOS、iPad 等平台共享业务语义，但不必强行使用相同布局。桌面窗口、触控导航、键盘和指针交互，应分别服从所在平台的习惯。

### 设计要具体到交互

我需要从最大结构一直到具体组件的设计，而不是只有一张应用外壳图。至少说明：

- 应用、窗口、场景与工作区之间是什么关系。
- 导航、主体内容、上下文区域、任务区域和常驻附件分别承担什么职责。
- 列表、表格、网格、编辑器、表单等工作区如何选择与切换。
- 工具栏、搜索、筛选、排序、选择、菜单、检查器、弹窗和设置如何操作。
- 空、加载、错误、无权限、离线、部分成功、取消和完成时发生什么。
- 多窗口、返回、恢复、关闭、拖放、快捷键和焦点如何影响状态。

组件是否出现取决于任务，不要求每个页面都塞满所有区域。

### 图示形式

设计文档使用等宽文本框图，不生成图片，不做 HTML 展示，不为看图调用浏览器或 computer use。图要表现具体结构和交互；用箭头、编号和简短说明表示触发、状态变化与去向。

```text
┌──────────────────────────────────────────────────────┐
│ WINDOW：窗口标题 / 系统工具栏 / 当前任务操作            │
├────────────┬──────────────────────────┬──────────────┤
│ NAVIGATION │ WORKSPACE                │ CONTEXT      │
│ 我在哪里   │ 我正在操作的主要对象     │ 当前对象详情 │
│ 区域与来源 │ 列表 / 编辑 / 表单等     │ 按需出现     │
├────────────┴──────────────────────────┴──────────────┤
│ TASK：需要时展开的任务、控制台或阶段进度               │
├──────────────────────────────────────────────────────┤
│ ACCESSORY：需要持续可见的播放、传输或状态               │
└──────────────────────────────────────────────────────┘
选择对象 → 更新详情；关闭详情 → 保留当前对象与工作进度。
```

文本图表达信息与行为，不表示必须绘制这些边框，也不替代系统组件的真实视觉效果。

## 4. 技术与架构方向

采用现代 Swift、SwiftUI 优先的 Apple 原生路线。已有技术方向以 Swift 6 和新系统能力为目标；具体系统版本、语言模式和兼容范围以当前任务及项目配置为准，不能把目标误写成已完成事实。

必要时通过平台内部适配使用 AppKit / UIKit。平台实现细节应留在适配边界，不应迫使业务功能依赖窗口控制器或其他平台对象。

### 我希望守住的边界

- **应用装配**：组合能力、依赖、入口与生命周期策略。
- **场景与窗口**：管理本场景的导航、选择、呈现、恢复和退出。
- **Feature**：承载有实际状态与行为复杂度的功能；简单视图不必被迫拥有一套运行时。
- **业务能力**：业务规则、用例与业务对象；可被不同界面调用。
- **基础设施**：持久化、文件、网络、系统服务与第三方接入。
- **界面与平台适配**：呈现业务状态，把用户动作交给正确的处理者。

状态要有明确所有者与生命周期。场景内选择和导航通常属于场景；跨场景共享的能力按产品语义归属应用。不要因某个状态方便访问就把它变成全局状态。

异步工作要定义取消、过期结果、重复操作、场景关闭和错误传播的行为。持久化与恢复要定义损坏数据、迁移和部分失败的处理方式。

### 对框架的期待

优先抽取已经被真实需求证明的共性。不要预先建设万能运行时、万能仓库、万能协议或把所有业务翻译成通用配置的系统。

框架提供能力与边界，产品保留表达自身语义的自由。抽象是否成立，取决于它是否减少真实重复和耦合，而不是名字是否足够通用。

### 前后端

需要清晰说明本地、系统服务、外部服务和自有后端各负责什么；不默认每个产品都必须建设后端。

需要后端时，明确契约、身份、授权、数据所有权、同步、冲突、幂等、失败恢复和版本演进。客户端与服务端通过契约协作，不把数据库结构直接当成全部产品 API。

不能仅因蓝图中存在某项能力，就未经当前任务范围判断立即实现它。

## 5. 代码与交付要求

每个视图应有可用的 `#Preview`。预览应使用确定的示例状态，避免依赖真实账号、网络、个人数据或会产生真实副作用的服务。复杂视图还需要能够检查关键状态，而不只是一个成功画面。

重构要落到目录、职责、依赖和调用关系，而不只是改名。删除旧代码前确认它确实退出使用；保护已有有效修改。迁移必须收口，不能让新旧路径长期同时承担同一职责。

验证应与风险匹配：构建、必要测试、架构约束与主要行为检查。报告实际验证过的内容和未验证的边界，不把历史通过记录当作当前版本的验证。

文档描述目标，代码说明当前实现；两者不一致时明确差距，不伪造“已经完成”。

## 6. AI 应怎样与我合作

我在意 token 和成本。回答应简洁、准确，尽量内部推理；不要长篇复述要求、反复播报过程或重复读取相同材料。

能根据现有信息确定的事情直接处理。确实依赖实现细节时，才读取最小必要范围；需要当前外部事实时再查证。若我明确说本次不搜索、不读文件，就遵守这个限制，不把它当成所有未来任务的永久禁令。

明确的工作请求意味着执行，不是仅给计划或问“要不要继续”。在已授权范围内完成合理的可逆操作；只有缺少关键输入、存在实质歧义或越过授权边界时才提问。

发现我的方案不合理时，直接说明具体问题并给出更好的落地方式。不要为了迎合而堆砌复杂设计，也不要擅自把我的核心目标换掉。

我要求写文档时，直接写到仓库合适位置，并更新入口。聊天只报告结果和文件位置，不把整篇正文再发一遍。

只增加长期有用的文档。优先更新现有职责对应的文件，避免一次任务产生一个临时总结、一套重复蓝图或多个互相矛盾的入口。

## 7. 意图不等于无限授权

本文是长期方向，不是要求每次任务重构全仓库，也不是自动授权发布、删除数据、部署或与他人通信。每次任务仍由用户当次请求确定范围。

不要声称能够让实现与用户想象绝对一致。应通过具体结构、明确行为、可检查实现和有效验证，逐步减少偏差。

## 8. 完成前的判断标准

1. 解决了当前真实需求，而不是只增加抽象或文档。
2. 交互符合 Apple 原生习惯，并且主要状态与边界行为明确。
3. 状态、任务、数据和平台细节各有明确归属。
4. 当前实现路径清晰，迁移遗留已处理或明确列出。
5. 相关预览与必要验证可用，结果如实记录。
6. 长期设计和工作队列可从统一入口找到。

遇到取舍时，优先顺序为：用户最新明确要求 → 当前任务的正确性与完整性 → 原生体验与清晰边界 → 复用与未来扩展 → 表面一致与抽象数量。
