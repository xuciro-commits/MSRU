# Apple 产品与应用基础框架总蓝图

版本：1.0 · 2026-09-20 · 规划视野：2026—2031 · 状态：建议采用的顶层设计基线

## 0. 这份文档承诺什么

你的要求合理，但“终极”应指**有能力持续裁决设计问题**，而不是今天冻结未来五年的类、数据库和界面。我们要建设的是一套可持续交付 Apple 产品的工程体系：真实产品是目的，AppFoundation 是降低重复成本的工具。

长期冻结原则与责任边界；定期更新技术方案；让新抽象通过真实产品检验。五年后仍应成立的是“谁拥有数据、谁承担失败、谁可以改变状态”，而不是某个 Swift 类型名。

本蓝图综合四份原始说明书，也采纳本仓库上一轮定向审计。原文中的“下一轮”“现在实现”“必须冻结六个类型”等是历史阶段建议，不是本次执行指令。本次交付文档与纯文本结构/交互图，不修改应用生产路径、不建立云服务、不宣布框架已实现。真实视觉采用 Apple 原生控件与系统 Liquid Glass；文本图只定义结构和行为，不模拟材质、截图或网页外观。

## 1. 产品使命与适用范围

开发者主要表达业务对象、行为、规则和呈现；框架减少窗口、场景、异步任务、命令、依赖、恢复和预览的重复机制。框架不替产品定义业务模型，不承诺消除所有平台集成代码。

| 产品类型 | 框架可复用部分 | 必须属于产品的部分 |
|---|---|---|
| MSRU / 媒体工具 | 多窗口、工作区、命令、任务所有权、辅助区域 | 曲库、播放队列、解码、内容来源、播放器 |
| 酒店 PMS / ERP | 工作台、选择与详情、工作流呈现、权限状态显示 | 房态、库存、价格、预约冲突、审批、账务 |
| Finder 类工具 | 导航、集合呈现、预览区域、长任务进度 | 文件访问授权、文件身份、复制冲突、磁盘操作 |
| IDE / 文档工具 | 场景、编辑工作区、辅助区、命令与恢复 | 文档一致性、编辑模型、语言服务、编译与调试 |
| 小型菜单栏工具 | 依赖、任务与测试等按需能力 | 不必存在完整 Shell、Workspace 或 FeatureHost |

这些例子是边界检查，不是已经实现的通用性证明。首要实证产品继续是 MSRU；酒店预订切片作为第二种压力测试，不重新开启一个完整 PMS 项目。文档工具用于验证非 CRUD 的所有权与内容模型。

保留原宪章的 macOS 第一参考平台与 MIT 开源目标；本蓝图不直接变更仓库许可或第三方组件许可。平台推进分层：当前闭环验证 macOS/iPadOS，iPhone 随紧凑交互用例推进，visionOS/watchOS 按设备特有任务分别验证。watchOS 可以只复用领域能力和任务机制，不承诺完整桌面 Shell。没有测试过的目标不能列为已支持。

## 2. 十二条长期原则

1. 每份可变状态、每个任务、每项持久资源有明确所有者和失效条件。
2. 业务实体身份独立于窗口、View、导航路径及当前显示模式。
3. 同一业务可有不同平台表达；共享语义不承诺同一界面结构。
4. 优先系统原生能力，允许局部下沉；不封装一个替代 SwiftUI/AppKit 的通用 UI 世界。
5. Feature 是能力与组合边界；简单页面不强制套齐 State/Action/Service/Host。
6. Feature 不直接控制另一个 Feature 的私有运行状态；协作通过显式业务能力或应用编排。
7. 依赖可替换；Preview/Test 不悄悄触达真实账户、网络或用户数据库。
8. 异步取消与旧结果失效是两个责任；两者都必须落实。
9. UI 恢复、领域持久化、缓存、同步各有契约，不互相冒充。
10. Foundation 不包含 Music、Reservation、Order 等产品规则；后端也不成为所有产品的共同业务模型。
11. 抽象必须减少真实重复与决策数量；案例类比、漂亮 API 和大量泛型不算证据。
12. 每次演进都能交付可用产品；不得长期保留两套正式运行路径。

| 层级 | 内容 | 变更方式 |
|---|---|---|

## 4. 目标系统结构

下面是逻辑边界，并非要求立刻创建这些 package、服务或仓库。箭头表示依赖或调用。

```text
产品组合根 / 平台入口
 ├─ 安装 Feature 与工作流
 │   ├─ 调用产品业务能力与规则
 │   ├─ 使用 AppFoundation 的任务 / 依赖 / 路由机制
 │   └─ 贡献 AppFoundationUI 的呈现描述
 ├─ 选择平台 Renderer → SwiftUI / AppKit / UIKit
 └─ 注入产品能力契约的实现
     ├─ 本地存储 / 文件 / 系统 SDK
     └─ 可选 API client
         → 产品后端 API
         → 授权 + 业务模块
         → 业务数据库 / 对象存储

框架内部依赖：AppFoundationUI → AppFoundation
禁止反向依赖：AppFoundation → UI / 产品业务
业务规则依赖能力契约，不依赖具体 View 或 Renderer。
```

领域规则不依赖 UI/Renderer。Feature 可以组合 UI 与业务能力，但不通过 View 发起未经领域契约约束的数据修改。产品内部的小用例不强求单独协议文件；先出现替换、隔离或测试需求，再提取能力边界。

**现在保留两个框架 target。** AppFoundation 承载依赖、Feature 运行机制、类型化路由和静态贡献；AppFoundationUI 承载呈现及原生适配。Platform 目录集中 AppKit/UIKit。未来 Testing/Networking/Sync 等只有在真实消费者和独立依赖成本出现后才考虑可选包，不列为必建清单。

服务端是按产品选择的可选部分，绝不成为启动桌面应用的默认前提。未来 Web 管理端消费相同业务 API，但有自己的 UI 和会话实现，不运行 Apple 的 Shell Renderer。

## 5. 统一概念，不统一所有对象

| 概念 | 正式含义 |
|---|---|
| Application | 进程与应用级装配、资源协调；不是所有状态的中央 Store |
| Scene | 独立交互会话，承载导航、选择、呈现偏好和场景任务 |
| Feature | 可识别的业务能力；静态声明与运行实例分离 |
| Runtime | 真正拥有状态、任务或外部资源，并能停止的对象 |
| Route | 可以定位和导航到的业务目的地，不是屏幕截图或 View 类型 |
| Workspace | 主要工作内容及其操作上下文；不等同于磁盘项目、文档集合或租户 |
| Shell | 组织工作区和辅助区域的呈现结构；不认识具体业务 Route |
| Presentation | UI 边界上的意图、内容构造和操作；不作领域数据或网络 DTO |
| Renderer | 将呈现映射到原生控件，维持状态与交互同步 |
| Workflow | 具有开始、提交、取消、失败与恢复语义的用户目标流程 |
| Auxiliary region | 控制台、日志、批处理结果等辅助工作区域，和 Workflow 分开 |
| Dependency / Service / Provider | 分别是交付能力的关系、完成用例的能力、同类能力的来源实现；不是规定每个用例必须经过的三层 |

`ApplicationShellRuntime` 当前更接近无状态组合器。它可以保留实现或在适当时机更名，但不能吸收上述所有责任。架构完整不等于拥有一个名为 `ApplicationRuntime` 的类型。

### 最小应用组合契约

Feature 在自身边界声明路由、导航入口、命令，以及需要时的设置贡献；应用显式安装一次，组合器归一化并校验，平台分别呈现。贡献是描述，不直接夹带原生窗口或业务运行对象。业务 UI 的构造仍在 AppFoundationUI 边界。

验收目标：安装一个测试 Feature 后，其已声明的导航、目的地、命令以及已支持的设置入口来自同一次注册；移除后也一起消失。重复 ID、无目的地入口、冲突的路由所有权应失败。新增 Feature 不需要修改 Renderer 和无关 Feature，不在多个中央 switch 重复登记同一事实。类型化 Route 枚举和显式安装清单仍可有必要改动，不追求运行时自动发现。

这是目标契约，当前实现尚未覆盖全部设置/命令呈现能力。先扩展已有 ApplicationDefinition 的真实需求，不同时再造另一套注册 DSL；用户权限变化可以改变可用贡献，但不能隐式创建 Scene 类型。

## 6. 生命周期：三层入门，多轴所有权

Application → Scene → Feature 是默认模型，不能当成万能树。Document 可以被多个 Scene 引用；账户可以在同一进程中切换；一个导入任务可能需要在关闭发起窗口后继续。

```text
Application owner
 ├─ Account session（按需）
 │   └─ 账户级业务资源
 ├─ Scene A → FeatureHost A → 已登记任务
 ├─ Scene B → FeatureHost B → 已登记任务
 └─ 被显式提升为应用级的后台工作

Document owner（按需，独立管理文档寿命）
 ├─ 被 Scene A 引用
 └─ 被 Scene B 引用

关闭 A → 停止 A 的工作、释放其文档引用
       → 不自动关闭 B、共享文档或应用级工作
```

每个对象明确三件事：**谁销毁它、在哪里可见、是否持久化**。例如播放服务属于 Application，迷你播放器在每个 Scene 呈现，播放历史另行持久化。跨工作区可见的 accessory 并不因此成为应用单例。

| 事件 | 必须明确的行为 |
|---|---|
| 关闭 Scene | 取消该场景工作、撤销回传/观察权限；共享文档/播放是否继续由其所有者决定 |
| 切换账户/组织 | 使旧授权、依赖和结果代次失效，切换缓存分区；不可把旧请求结果显示给新身份 |
| 离开 Feature | 根据产品策略取消或保留；SwiftUI View 暂时消失不是业务寿命的可靠定义 |
| 进入后台 | 保存可恢复意图，并服从平台执行限制；不承诺无限后台任务 |
| 退出/崩溃 | 退出可补写但不是唯一保存机会；崩溃恢复以最近成功写入为准 |

Scene 类型和平台入口显式声明；窗口实例与权限可见性允许动态变化。Primary Scene Strategy 是产品主入口的默认策略，可以组合主窗口、文档和菜单栏，不强制每个产品只能选一种。

## 7. 行为、命令与路由

默认行为链：输入 → 当前 Scene/Feature 的 action → 同步状态转换/调用能力 → 异步结果 → 验证有效性 → 状态 → 呈现。小型本地控件状态可以直接使用原生 Binding；领域操作、失败与异步结果必须可追踪。

菜单、toolbar、快捷键和 context menu 若表达同一业务操作，应调用同一用例及可用条件。命令的目标场景由焦点/明确请求决定，不靠全局“当前选中项”。`ApplicationCommand` 不升级成容纳所有业务 action 的万能总线。

Route 与显示模式默认分开；但共享链接可能需要携带筛选、时间范围或模式。应把它们作为可选、可校验的呈现参数，而不是颁布“显示模式永远不能进 URL”的禁令。参数化路由使用穷尽分派或可验证 case 映射；任意匹配闭包不能宣称被编译期完整证明。

Workflow 的“取消界面”不自动撤销已经提交的业务交易。导入可取消未完成步骤；已提交预订需走取消预订用例。高价值提交前后的状态必须在产品中清楚可见。

## 8. 五年内应稳定的交互语言

```text
窗口 / 场景
 ├─ 原生命令与导航栏
 ├─ Navigation：可去的地方
 ├─ Workspace：当前主要工作
 │   ├─ 身份、内容、类型化选择
 │   ├─ 局部操作、查询与显示方式
 │   └─ 可选工作区 accessory
 ├─ Context：检查器 / 预览 / 活动 / 工具
 ├─ 可选跨工作区 accessory
 └─ 可选 auxiliary region

Workflow：按目标和平台选用 sheet、导航过程或独立窗口
```

完整 Shell 中 Workspace 是中心，但工具应用无需强行创建 Shell。不要把每个区域都变成必须公开的 Swift 类型；先让布局与行为契约成立。

平台策略消费：当前可用空间、输入方式、区域角色和任务需求。它可以调整区域位置，却不能偷偷改变数据所有权、命令目标或提交语义。不同平台允许使用不同内容 View；不追求整个视图树共用。

附属区域隐藏后必须可找回；关键操作不能只存在于窗口底部；搜索不应无理由重复；表单、表格、时间轴和画布使用各自适合的信息密度。逐页面结构及交互见[文本图谱](InteractionAtlas.md)。

## 9. 当前技术方案与可替换边界

| 项目 | 起始选择 | 何时重新考虑 |
|---|---|---|
| Apple 客户端 | Swift 6 语言模式、Observation、SwiftUI 优先；必要时框架内部 AppKit/UIKit | 原生能力缺口、可测性能问题或 SDK 演进 |
| 最低系统 | 当前项目按 OS 27 基线推进；各平台须实际构建与验收 | 新产品设备群与维护成本变化；不是五年不变的版本号 |
| UI 状态 | 按所有者划分可观察状态；FeatureHost 按需使用 | 出现实际重复机制，不因统一形式重构全部页面 |
| 本地数据 | 小型配置可文件存储；复杂查询/事务选择 SwiftData 或 SQLite 适配 | 按产品数据契约与迁移测试决定，不在 Foundation 固定 ORM |
| 组织后端 | 首个真实需要时启用模块化单体、PostgreSQL、HTTP JSON/OpenAPI | 可测部署/规模/团队边界要求拆分时 |
| 后端语言 | 条件性默认 TypeScript + Node 的受支持 LTS；全 Swift 团队可选 Swift 后端 | 做一个含授权、事务、迁移和测试的完整切片后锁定该产品方案 |
| Web 管理端 | 有真实用户与渠道需求再建，复用 API 契约 | 不能仅为了“全栈完整”提前创建 |

AppFoundation 暂按源码 package 分发；没有二进制分发需求，不提前增加 ABI 稳定成本。OS 支持列表、协议 API、最低版本必须区分“声明可用”和“已测试支持”。

## 10. 数据正确性与可运营性

个人本地工具可以没有服务器；个人同步不等同于组织业务；多人交易由服务端确认业务不变量。用户数据必须有可迁移 schema、可验证备份或导出，以及明确删除语义。同步、副本、UI 恢复都不能替代备份。

服务端承接组织权限、跨用户一致性、审计与权威提交；客户端承接低延迟交互、草稿和离线可用性。无法安全离线完成的动作明确显示“待提交/需联网”，不显示虚假的成功。具体协议、冲突和幂等示例见客户端/服务端架构。

日志沿用场景/请求/操作 ID 关联行为，避免把敏感业务正文写入常规日志。先用平台日志、基础指标和错误报告，实际排障不足时再增加 tracing 系统。商业系统必须能观察失败提交、积压任务、同步冲突、备份恢复结果，而不只是服务是否在线。

## 11. 进入 Foundation 的资格

每次提取应回答：

1. 哪些真实产品代码正在重复同一机制？复制的是行为，而不只是外观或文件名吗？
2. 至少两个独立真实用例是否具有相同寿命、失败语义和替换边界？跨产品证据更强。
3. 提取后，业务代码是否减少概念、状态同步与维护点？
4. 是否能独立 Preview/Test，且允许原生/产品扩展而不无限增长配置？
5. 原实现能否在本阶段删除？不能时为什么值得先提取？

只有一个产品的稳定机制可以放在内部实验区域，不急着公开、承诺稳定。禁止为了满足数量编造 dummy consumer。框架 API 在实验 → 产品内验证 → 多用例验证 → 稳定发布之间推进；进入稳定阶段才采用明确 SemVer 和弃用窗口。

原生 primitive 默认直接使用。通用 Card、万能 Repository、动态插件发现、任意 docking、全局 Selection/FocusRuntime、微服务集群、通用 ERP schema 均不列为框架建设目标。它们未来可以有独立证据，但今天不获授权预算。

## 12. 演进路线：按证据开门

| 阶段 | 交付结果 | 必须通过的门槛 | 退出与下一步 |
|---|---|---|---|
| A：可靠性基线 | 收敛当前迁移；修取消、场景失效、恢复容错；启用 Swift 6 语言模式 | 原有测试 + 非协作取消/关闭后回调/损坏快照；macOS 与 iPad build；一次真实双窗口退出恢复验收 | 冻结新增基础概念，进入真实用例 |
| B：MSRU 跨平台闭环 | Browse 搜索切片，再接 Library 收藏/本地持久化/播放器 | 两平台能完成相同业务；呈现不同；query/toolbar/选择同步正确；弱网、空态、失败可用 | 回到产品开发；不继续补齐设想中的所有 renderer |
| C：异类切片 | 酒店预订时间轴 + 草稿/提交/冲突；再挑一个文档/文件用例 | 自定义 Surface 无须修改框架核心；领域正确性属于产品；能明确删除重复机制 | 只提取证据充分的重复；决定是否需要独立后端 |
| D：稳定发布 | 实际被多个用例使用的 package、模板与契约测试 | 新功能无需改 Renderer 或无关 Feature；新 SDK 升级成本可控；API 迁移有路径 | 维护少量稳定能力，不追求框架覆盖率 |
| E：持续演进 | 产品需求驱动的能力增量 | 每项新框架投入都有产品收益、负责人和停止条件 | 没有新证据就不扩大框架 |

这不是五个年份的流水账。建议第一年争取 A/B，C 由第二产品需求触发，其余随真实使用推进；没有团队容量与用户数据，不能承诺某年必须完成某框架。

默认把多数开发时间用于产品；框架建设以明确痛点设有界任务。连续两轮架构工作都没有可体验收益或删除重复，应停止新增概念，回到产品切片。记录几个可对比指标即可：新增 Feature 改动了哪些无关模块、首个 Preview 耗时、跨平台适配点、退出恢复失败、公共 API 破坏次数。先建立基线，不虚构目标百分比。

## 13. 完成定义与开发任务模板

一项功能完成意味着：用户能从入口到结果走完；失败/取消/重试清楚；状态所有者明确；Preview 不使用 live；相关契约测试通过；平台输入与无障碍可用；持久化变化有迁移/回退判断；旧路径已删除。并非每项功能都要增加测试文件，测试必须验证真正风险。

```text
用例与目标用户：
成功结果与失败行为：
数据权威 / 状态所有者 / 停止条件：
已有能力及最小新增能力：
客户端与服务端责任（无服务端则写无）：
平台呈现差异：
Preview fixture / 契约测试 / 人工验收：
迁移和删除内容：
本阶段不做的事项：
```

最终判据：你能否更快、更可靠地做出第二个产品，同时让第一个产品继续变好。若做产品必须先理解越来越多的框架名词，方向就需要纠正。
