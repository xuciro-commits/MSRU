# 客户端与服务端技术架构

本文件是[总蓝图](ProductPlatformBlueprint.md)的可更新技术方案。“前端”指 Apple 原生客户端；“后端”指产品需要时启用的远程业务系统，而不是把本地 Store 改名叫后端。以下后端尚未创建。

## 1. 先选数据模式

| 模式 | 权威数据与依赖 | 适合 | 不应强加的设施 |
|---|---|---|---|
| 本地应用 | 本地文件/数据库，必要时直连系统或外部 provider | MSRU 起步、Finder 工具、个人编辑器 | 自建账号、通用服务器、消息队列 |
| 个人同步 | 本地可用副本，按明确规则在设备间收敛 | 收藏、偏好、个人文档元数据 | 自动推导企业权限/审批系统 |
| 组织业务 | 服务端权威提交；客户端缓存、草稿与待提交命令 | PMS、ERP、多人库存与审批 | 客户端自行确认共享库存/房态成功 |

同一产品可以混合：MSRU 音频文件由本地或 provider 管理，个人收藏可以同步，订阅权益由相应服务验证。禁止让所有对象先经过一个“统一数据层”。

CloudKit 支持私人数据与用户间共享，不能简单说它“不支持多人”。其共享内容保留于拥有者私有数据库，参与者获得共享视图；因此企业组织生命周期、租户权限与交易规则仍须单独评估。这是选择独立组织后端的理由，而非 CloudKit 的一概否定。[Apple 共享记录模型](https://developer.apple.com/documentation/CloudKit/shared-records?changes=l_9)

## 2. 客户端结构

```text
App / Scene composition
  ├─ Feature 状态与动作 → 用例能力
  ├─ 呈现 → 平台 Renderer
  └─ 注入：本地适配器 / API client / 身份会话 / 时钟等

用例能力
  ├─ 产品领域校验与业务编排
  ├─ 本地读写与缓存
  └─ 可选远程提交与同步协调
```

依赖默认通过构造或现有 typed DependencyValues 交付；不创建能随时解析所有对象的全局 service locator。应用/账户服务可共享，Scene 导航、选择和呈现独立；只给 Feature 所需能力，不默认传递整个 ApplicationModel。

MainActor 管理 UI 状态；长 I/O 使用异步 client；CPU 密集处理选择明确执行边界；actor 用于真正共享的可变资源。跨边界请求/结果须 Sendable。任务所有者登记 token/代次，取消或切换身份后拒绝旧结果；仅调用 `Task.cancel()` 不足以证明状态正确。

Framework 提供机制，产品选择用例契约：`LibraryRepository` 可以保留，不要求所有网络 client 都有 Repository；一个简单 client 已可测试时，不叠加 Repository → Service → Manager。

## 3. 组织后端的起始方案

在第一个确实需要组织协作的产品中，用**一个可部署的模块化单体**开始：

```text
[Apple 客户端] / [可选 Web 管理端]
                 │
                 ▼
        [HTTPS / API 入口]
                 │
                 ▼
       [身份验证与租户授权]
                 │
                 ▼
          [产品业务模块] ────→ [附件对象存储]
                 │
                 ▼
           [PostgreSQL]
                 │
                 ▼
      [事务 Outbox / Worker]
                 │
                 ▼
         [通知 / 外部系统]
```

一个代码库、一个主要数据库，API 与 worker 可先用同一代码包的不同进程。组织/成员管理作为公共支撑模块；Reservations、Inventory、Orders 仍是产品模块，不先开发覆盖所有产品的业务平台。模块拥有自己的写入口，不能随意改其他模块表。

条件性技术默认：TypeScript、Node 受支持 LTS、一个成熟 HTTP 框架（候选 Fastify）、PostgreSQL、对象存储、成熟 OIDC 身份服务、OpenAPI 契约。若全 Swift 团队维护同等切片明显更容易，可改 Swift 服务端；这是实施前验证项，不是最高原则。不要同时维护两套后端。部署商、地区、运行版本、框架版本在产品 ADR 中锁定，本次不凭空选供应商或承诺价格。

不默认引入 Kubernetes、微服务、Kafka、独立搜索集群或通用事件溯源；容量、隔离或组织边界达到实际瓶颈再调整。数据库中的业务事件/审计记录与全系统 event sourcing 是不同成本。

## 4. API 与错误契约

以产品用例和稳定资源为边界。OpenAPI 是可审阅契约，客户端可生成传输 DTO；DTO 映射到产品模型，不直接暴露数据库结构，也不跨端共享 SwiftUI/Observation 对象。

| 接口面 | 起始约定 |
|---|---|
| 身份 | 原生应用使用授权码 + PKCE 与系统授权会话；不在 App 内嵌服务端 client secret |
| 授权 | 每次请求验证令牌及组织成员/资源权限；客户端隐藏按钮仅改善体验 |
| 读取 | 分页、稳定 ID、明确排序；时间用有时区意义的格式，酒店营业日期另有业务时区 |
| 修改 | 带资源版本/强 ETag 的条件修改；原子校验后提交 |
| 重试 | 客户端操作 UUID；服务端持久化幂等结果和请求摘要 |
| 错误 | 稳定 error code、request ID、可选字段错误；UI 本地化说明，不解析后端自然语言 |
| 演进 | 优先兼容性新增；破坏性变更版本化，按活跃客户端与升级策略退役旧版本 |

原生 OAuth 的系统浏览器/外部用户代理和 PKCE 要求有明确标准依据；OIDC 身份并不自动授予产品操作权限。[RFC 8252](https://www.rfc-editor.org/rfc/rfc8252.html)

错误区分未登录、无权限、校验失败、版本冲突、资源不存在、限流和暂时不可用。自动重试只针对可安全重试的操作，结合退避与服务端指示；不得靠重试掩盖业务拒绝。若 `If-Match` 条件失败，应按协议返回 412；业务冲突可以另用 409。[RFC 9110 §13.1.1](https://www.rfc-editor.org/rfc/rfc9110.html#section-13.1.1)

## 5. 一个完整用例：修改预订

```text
时间向下；每一步标明发送方、接收方与动作。

① 预订 Feature → 本地草稿/待提交记录
  保存草稿，生成 operationID
                 │
                 ▼
② 预订 Feature → 预订 API
  提交修改 + expectedVersion + operationID
                 │
                 ▼
③ 预订 API：认证、租户成员及资源权限
                 │
                 ▼
④ 预订 API → 数据库事务：幂等检查、版本/房态校验
                 │
                 ├─ 可以提交
                 │   数据库事务：修改预订 + 审计 + Outbox + 幂等结果
                 │   数据库事务 → 预订 API：原子提交
                 │   预订 API → 预订 Feature：新版本与确认结果
                 │   预订 Feature → 本地草稿/待提交记录：标记已确认并合并结果
                 │
                 └─ 已被修改或房态冲突
                     数据库事务 → 预订 API：拒绝，不提交部分修改
                     预订 API → 预订 Feature：冲突及允许公开的最新信息
                     预订 Feature → 本地草稿/待提交记录：保留草稿，等待用户处理
```

网络断开时客户端可能不知道服务端是否已提交。重试必须复用同一 operationID；服务端按租户 + 操作类别 + key 唯一保存结果，同 key 不同参数拒绝。保留期和超期处理须明确，不能宣称全系统“exactly once”。外部通知通过事务 outbox 派送，消费端去重；重试/死信必须可观察。

两个用户同时订同一房间，不能靠“先查询没有，再插入”保护。用数据库约束、明确锁或合适隔离级别维护业务不变量；失败时重试完整事务。PostgreSQL 默认 Read Committed 不是所有业务冲突的自动保险。[PostgreSQL 事务隔离](https://www.postgresql.org/docs/current/transaction-iso.html)

## 6. 离线与同步

| 数据/操作 | 离线策略 |
|---|---|
| 个人偏好 | 允许本地即时修改；可采用明确的字段合并规则 |
| 收藏集合 | 用稳定身份及删除语义处理增删；不把下载缓存当收藏本体 |
| 组织记录浏览 | 显示缓存及更新时间，权限失效后按策略清除/隔离 |
| 预订/订单草稿 | 本地保存、可恢复、标记未提交 |
| 库存扣减、房态确认、审批 | 默认需服务端确认；离线只能排队请求或明确禁止 |
| 本地文件编辑 | 按文档模型持久化；外部修改和多窗口编辑需单独协调 |

待提交状态至少可区分待发送、发送中、已确认、冲突、被拒绝。短暂错误与业务冲突不能共用无限重试队列。账户/租户切换须隔离队列及结果。

```text
[待发送] ──发出已持久化的命令──→ [发送中]
                                  │
                                  ├─ 服务端确认提交 ──→ [已确认]
                                  ├─ 版本/业务冲突 ───→ [冲突]
                                  ├─ 明确业务拒绝 ────→ [拒绝]
                                  └─ 超时、断网或中断，无法确定提交结果
                                                   │
                                                   ▼
                                               [未知结果]
                                                   │
                         恢复后重试同一 operationID、同一组参数
                                                   │
                                                   └──→ [发送中]

[冲突] / [拒绝]：保留草稿，等待处理，不自动无限重试。
用户修订后再次提交属于新命令：生成新 operationID → [待发送]。
```

若实现增量同步，必须处理游标过期后的全量重建、分页一致性、删除 tombstone、权限撤销和重复事件；推送只是刷新提示，不是唯一数据来源。只在真实离线要求出现后实现，不在 AppFoundation 一开始建立通用同步引擎。

## 7. 迁移、恢复与运维底线

客户端数据库版本、服务端数据库版本、API 版本和 Scene snapshot 版本分别管理。数据库用可重跑/可验证迁移；破坏性调整采用先扩展、迁移、再收缩，覆盖旧客户端并存期。发布回滚不等于可以自动反向执行破坏性数据库迁移。

Scene 快照只保存稳定定位与必要 UI 线索；文档内容、用户资产和交易不能只放在 UI 恢复存储。恢复坏记录要隔离保留原文，不用空结果覆盖整份数据。后台/终止通知都不能作为唯一保存机会。

组织系统上线前明确可接受丢失量与恢复时长；自动数据库备份/时间点恢复、附件版本或备份、密钥恢复流程及实际恢复演练缺一不可。个人产品至少应有可验证导出/备份路径及迁移失败保护。不要把同步副本当备份。

最小验收包括：跨租户访问被拒绝、重复提交不重复生效、版本冲突不覆盖、断网重启可恢复草稿、备份可还原、旧客户端兼容、权限撤销生效。生产日志去除敏感内容，保留关联 ID 以便用户报告问题。

## 8. 哪些可以进入框架

先留产品：领域 schema、Repository 协议、权限规则、同步合并规则、交易与审计、后端业务模块。

可在多个产品验证后提取：小型传输适配、凭据存储适配、错误呈现约定、任务进度/同步状态的 UI 宿主。它们是可选能力，不加入每个应用都必须启动的总 Runtime。

以上协议事实由链接资料支持；模块化单体、语言默认、产品边界及迁移节奏是本蓝图的设计建议，不是标准规定。
